# Document Artifact Normalization

Honeycomb treats an explicit document request as a file-delivery contract, not
as a successful text reply. This applies to required MD, TXT, JSON, CSV, PDF,
DOCX, PPTX, and XLSX deliverables, and to text/file results requested for the
desktop, a registered workspace, or an approved custom directory.

Ordinary conversation text with no requested document format and a
`conversation` target remains a chat reply. It does not create an unnecessary
file-delivery gate.

## Completion Contract

A required document is complete only when all of these conditions hold:

1. A non-empty regular file exists inside the job work directory.
2. Honeycomb validates the file from its bytes instead of trusting its name.
3. A canonical `agent.artifact_files` row records format, MIME type, byte count,
   SHA-256 checksum, source, and structural metadata.
4. An `agent.artifact_deliveries` row reaches `succeeded` for the requested
   destination. Local targets require a desktop write receipt with matching
   byte count and checksum.

Missing, malformed, or undelivered required files move the job to
`waiting_for_human` with `required_document_delivery_missing`. A prose promise
or a text file renamed to `.pdf`, `.docx`, `.pptx`, or `.xlsx` cannot pass.

## Format Handling

| Requested format | Accepted or generated result |
| --- | --- |
| MD / TXT | Strict UTF-8, non-empty text with no NUL bytes |
| JSON | Strictly parsed object or array; formatted without inventing fields |
| CSV | Strictly parsed rows with consistent column counts |
| PDF | Real `%PDF-` file parsed by `pdf-lib` with at least one page |
| DOCX | Real OOXML package with Word package roots |
| PPTX | Real OOXML package with PowerPoint package roots |
| XLSX | Real OOXML package with Excel package roots |

Honeycomb can deterministically derive MD, TXT, JSON, CSV, PDF, and DOCX from a
validated child-agent text source. JSON and CSV generation proceeds only when
the source already parses as that exact structure. PPTX and XLSX must be real
files created by a child agent.

PDF output embeds a CJK-capable font for non-ASCII text. The Windows worker
uses an installed Chinese system font; the Linux worker image installs Noto
Sans CJK. `HONEYCOMB_DOCUMENT_PDF_FONT_PATH` and
`HONEYCOMB_DOCUMENT_PDF_FONT_FACE` can provide an explicit deployment font.

## Recovery And Safety

The source checksum, requested format, title, and normalizer version determine
the derived output path. A retry first validates and reuses an existing result.
If that result is corrupt, Honeycomb removes it, creates a fresh temporary
file, flushes it, validates the generated bytes, and atomically renames it.
Original child-agent files are never overwritten.

Document discovery rejects symbolic links and paths outside the job work
directory. Input/output bytes, text length, discovery depth, scanned entries,
ZIP entries, expanded ZIP bytes, individual ZIP entries, and suspicious ZIP
compression ratios are bounded through the `HONEYCOMB_DOCUMENT_*` settings in
`.env.example`.

Mock agent output is excluded from document sources. Simulation mode therefore
cannot satisfy a real document-delivery requirement.
