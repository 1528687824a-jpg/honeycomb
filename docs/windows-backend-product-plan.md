# Honeycomb Windows 后端产品计划

## 阶段 2 未知结果核对进展（2026-07-14）

“请求已发出但结果未知”的安全核对已经完成。模型请求发出前会先保存本地请求编号、服务商、模型、路由和尝试次数；服务商返回请求编号或视频任务编号后也会立即持久化。任务可以只读查询服务商状态，区分“仍在处理”“未受理”“失败”“成功”和“仍无法判断”，不会通过再次生成来试探结果。

存在未核对调用时，任务页、恢复接口、旧管理接口、数据库状态转换和 worker 都会阻止直接重跑。确认未受理或失败后才能安全恢复；确认成功后复用原结果。图片和视频还必须找回可下载的媒体地址，否则继续暂停，不能只凭“成功”文字把任务标成完成。任务页会显示 Agent、服务商、模型和核对状态，并提供自动核对及带风险提示的人工确认。

新增 `npm run smoke:model-reconciliation` 作为 PostgreSQL 验收脚本。Docker Desktop 与 PostgreSQL 当前保持关闭，因此本轮只完成脚本和类型检查，数据库实跑仍待运行环境开启。阶段 2 下一项改为“费用硬上限”。

## 阶段 2 重试进展（2026-07-14）

分类重试和退避已经完成：只有明确安全的临时故障才会自动重试，并遵守服务商返回的 `Retry-After`；API Key、权限、余额、模型名和请求参数问题不会在同一路由反复消耗。请求发出后结果不确定时，任务会暂停等待人工处理，不会盲目重试或切换服务商。

等待重试会保存为 `retry_waiting`，worker 重启后从原路由和下一次序号继续；任务页、时间线和运行统计都能看到重试状态，取消任务也会停止等待中的调用。未知结果核对与修复也已完成，阶段 2 下一项是费用硬上限。

## 最新进展（2026-07-14）

阶段 1 的代码实现已经完成，阶段 2 的“执行前检查”“持久并发队列”“运行中取消”“分类重试”和“未知结果核对”也已完成：

- 项目、对话、草稿、附件和消息已进入 PostgreSQL，并与任务双向关联；
- 面板 Agent 返回经过校验的结构化编排计划，模型不可用时才启用明确标记的确定性降级计划；
- 前端不再独立猜测任务类型、编排模式或参与 Agent；
- worker 直接执行任务记录中已经持久化的计划，不再重新做一套关键词判断；
- 同一条用户消息只能创建一个任务，项目/对话/消息保存与任务关联使用事务和幂等保护；
- 面板 Agent 只能选择本机已启用的子 Agent，所有正式任务强制由 `test-agent` 进行质量验收；
- 茶道海报基准会得到“茶道宣传海报”、`image-agent`、桌面 PNG、1080×1920，并跳过 research、writer、video；
- 每次任务启动前会检查实际参与的生产 Agent、`test-agent`，以及讨论模式的主 Agent；
- 检查范围包含 Agent 是否存在/启用、模型、Provider、真实本地 Key、接口地址、最近验证状态和图片/视频/文字能力类型；
- 主路线不可用时会检查备用 Provider 路线，只要存在可用路线就选择备用路线并记录警告；
- 检查结果持久化到任务并写入时间线。配置错误会在任何模型调用前把任务置为“等待人工”，不会盲目消耗 Token；
- HTTP、飞书、定时任务、会话分叉、任务恢复和 worker 最后一道检查都使用同一套规则；
- 任务页会说明具体哪个 Agent 缺少哪项配置，并提供“配置 Agent”和“恢复任务”入口；模拟执行会明确说明不会生成真实文件；
- 图片/视频 Agent 的实际验证类型优先于模型名称，因此 `ep-...` 一类不透明端点名不会被误判；
- 真实模型调用进入 PostgreSQL 持久队列，统一限制全局、同一 Provider 和同一 Agent 的并发数量；
- 默认上限为全局 4、每 Provider 2、每 Agent 1，可由环境变量或 Agent/Provider 元数据覆盖；
- 排队请求和已取得名额的调用都有带心跳的租约。worker 崩溃后旧记录自动过期，不会永久占用名额或挡住后续任务；
- 模型调用只有取得名额后才写入“已开始”，成功、失败和切换备用 Provider 都会按所有权安全释放名额；
- 任务列表会显示“排队”，详情显示 Agent、Provider、队列位置和三层占用；`GET /runtime/model-call-queue` 提供全局观察入口；
- 新增 `npm run smoke:model-call-queue`，用于真实 PostgreSQL 迁移、并发限制、独立 Provider 并行和释放后晋升验收；
- 用户取消任务后，worker 会通过数据库监听把取消信号传入正在运行的 Provider HTTP 请求、图片/视频下载、文件写入和 OpenClaw 子进程；
- Windows WSL 模式除了中止外层 `wsl.exe`，还会按唯一会话 ID 定向终止 Linux 内的 OpenClaw 进程，不会误停其他任务；
- 取消不会切换备用 Provider，也不会记成普通失败；模型调用使用独立的 `cancelled` 状态，并在任务时间线和运行统计中可见；
- 取消接口还会调用 DBOS 的原生工作流取消，停止重试和后续步骤；即使 DBOS 通知失败，任务取消仍然有效，并把失败原因写入时间线；
- 数据库会拒绝在已取消任务上开始新的模型调用，并用行锁消除读取旧取消状态的竞态；取消接口还会立刻清理残留的 `started` 调用；
- `npm run smoke:cancel-job` 已扩展为验证活动调用取消、取消后拒绝新调用、运行统计和时间线记录；
- TypeScript 检查、桌面端生产构建和全仓库 118 项单元测试通过。

本机 PostgreSQL 与 Docker Desktop 当前均未运行，因此数据库烟雾测试没有在本轮自动启动 Docker。`npm run smoke:conversation-persistence`、`npm run smoke:model-call-queue`、`npm run smoke:cancel-job` 和 `npm run smoke:model-retry` 等待后端运行时完成真实数据库验收。

## 产品目标

Honeycomb 的 Windows 版不是一个“能调用模型的演示面板”，而是一套本地多 Agent 工作系统：

1. 用户在项目对话中描述工作；
2. 面板 Agent 判断这是普通交流还是正式任务；
3. 面板 Agent 生成明确的任务名称、编排模式、参与 Agent、验收标准和交付位置；
4. 后端可靠执行，用户能看到任务进度和每个子 Agent 的真实状态；
5. 任务可以取消、重试、恢复，且不会因为重启而丢失或重复花费；
6. 图片、视频、文档等结果必须真正保存并交付，不能只显示“成功”；
7. 正式 Windows 版不应要求普通用户手动操作 Docker Desktop。

## 当前真实链路

```text
对话页
  -> 项目 / 对话 / 消息同步到 PostgreSQL
  -> POST /panel/chat（面板 Agent 返回回复 + 结构化编排计划）
  -> 前端只展示结果并提交已校验计划
  -> POST /jobs（携带对话 ID、来源消息 ID 和结构化计划）
  -> createJob 在事务中持久化任务并执行重复派发保护
  -> startJobWorkflow
  -> DBOS 工作流
  -> createPipelinePlan 读取任务中已持久化的唯一计划
  -> 四种编排模式
  -> OpenClaw 或 provider-direct
  -> Postgres / 任务文件 / artifact API
  -> 桌面端下载或导出结果
```

同一任务由三处重复判断的问题已经消除，并发、排队、运行中取消和分类重试也已有统一控制。当前主要风险已经转移到阶段 2 后半段和阶段 3：未知结果仍缺少服务商侧核对与自动修复；费用还没有硬上限；外部媒体下载失败时仍可能错误完成；视频异步任务也还缺少完整轮询和结果取回。

## 实施顺序

### 阶段 1：统一“对话 -> 任务”后端契约

状态：代码已完成；等待在运行中的 PostgreSQL/开发后端上执行 `npm run smoke:conversation-persistence` 后关闭运行时验收项。

目标：面板 Agent 成为唯一的任务规划者，前端只展示和提交，不再自行猜测。

交付内容：

- 在后端持久化项目、对话、消息，以及对话与任务的关联；
- 面板 Agent 返回结构化计划：
  - `intent`：普通回复或任务；
  - `title`：用户能看懂的任务名称；
  - `routingMode`：四种模式之一；
  - `selectedAgents` / `skippedAgents`；
  - `stages`、验收标准、输出类型、交付位置；
  - 模型调用预算和需要补充的问题；
- 后端校验这份计划后原子化创建任务，避免“回复成功但任务没创建”或重复派发；
- 关键词规则只保留为模型不可用时的降级方案，并明确标记为降级；
- 任务名称写入数据库，不再只由界面临时推断。

验收场景：

> “帮我做一个茶道宣传海报，1080×1920，古典华美，无文字，PNG，放到桌面。”

应得到：任务名“茶道宣传海报”；生产 Agent 只选 `image-agent`；`test-agent` 作为质量关卡；跳过 research、writer、video；交付要求明确为桌面 PNG。

### 阶段 2：执行控制与费用保护

状态：执行前检查、阻塞原因持久化、恢复入口、全局/Provider/Agent 并发队列、桌面排队可见性、正在进行中的请求取消、分类重试和未知结果核对修复已完成；费用硬上限仍待实现。

目标：任务跑得动，也停得住；失败不会盲目重试或重复扣费。

交付内容：

- 全局、每 Provider、每 Agent 的并发上限和排队状态；
- 取消信号传入正在运行的 HTTP 请求和 OpenClaw 子进程；
- 按错误类型处理重试：
  - API Key、模型名、余额/权限错误不自动重试；
  - 限流、临时网络错误、服务端错误按退避策略重试；
  - 支持 Provider 返回的 `Retry-After`；
- 继续使用幂等记录，补齐“请求已发出但结果未知”的自动修复；
- stalled 任务可从安全检查点恢复，不从头重复执行已成功阶段；
- 在执行前验证所有已选 Agent 的模型、Key、端点类型和账户状态；
- 记录调用次数、Token、估算费用和失败原因。

验收标准：取消后不再产生新的模型调用；认证错误不会连续重试；程序或 worker 重启后不会重复消费已完成的模型调用。

### 阶段 3：统一产物与交付

目标：任务“成功”必须等于用户真的拿到结果。

交付内容：

- 统一图片、视频、文档、外部 URL、Provider 异步任务的产物记录；
- 远程媒体优先保存到 Honeycomb 管理的本地存储，并记录校验值、格式、大小和来源；
- 下载失败进入可重试的交付状态，不能把只有临时 URL 的任务直接标成完整成功；
- 完成视频任务状态轮询、超时、取消和最终文件下载；
- 按用户要求执行 PNG/JPEG 等格式转换；
- 桌面、项目文件夹或自定义位置都通过统一交付任务处理；
- API 提供稳定的预览、打开、另存和重试交付能力。

验收标准：茶道海报任务结束后，桌面存在可打开的 1080×1920 PNG；任务页能预览，并能看到保存位置和交付状态。

### 阶段 4：把四种编排模式做实

目标：四种模式不是四个名称，而是四种可验证的执行行为。

- `supervisor_pipeline`：逐阶段执行，每个生产阶段经过质量检查和有限修正；
- `pipeline`：严格使用上一步产物，最后统一验收；
- `classic_master_slave`：真正并行执行互不依赖的子任务，再由主 Agent 汇总；
- `master_slave_discussion`：保留多方意见和轮次，再由主 Agent 综合结论。

每种模式都要覆盖：动态 Agent 选择、取消、限流、失败恢复、预算、产物、时间线和重启恢复。真实 Provider 测试需要继续获得用户明确授权。

### 阶段 5：Windows 本地运行与安装

目标：开发者可以继续使用 Docker，但普通用户不需要理解或手动操作 Docker Desktop。

交付内容：

- 短期：Honeycomb 启动时先打开界面，明确显示后台状态；未经用户设置，不突然启动 Docker Desktop；
- 正式发行：内置并监管 API、worker 和本地 PostgreSQL 运行环境；
- 保留 Docker Compose 作为开发和诊断模式；
- 提供一键启动、停止、修复、日志包、备份和恢复；
- 安装、升级和卸载不丢失用户项目、对话、配置和任务产物；
- 继续使用 Windows DPAPI 保存 API Key。

验收标准：在一台没有运行 Docker Desktop 的干净 Windows 机器上，安装后能完成首次配置、对话、真实任务、结果交付、退出和再次恢复。

### 阶段 6：发布级收口

目标：形成可重复验证的 Windows 发布候选版。

- 把超大的 `server.ts` 和 `activities.ts` 按已触及的功能边界逐步拆开；
- 建立 API 合约测试、数据库集成测试、四模式回归测试和桌面端到端测试；
- 覆盖断网、限流、Key 失效、磁盘不足、Provider 返回空结果、Docker/进程退出、数据库迁移失败等场景；
- 生成不含密钥的支持日志包；
- 完成数据库和产物备份/恢复；
- Windows 安装包、升级、卸载、签名和干净机器测试通过。

## Windows 发布候选门槛

只有以下条件全部满足，才恢复 macOS 主线：

1. 对话、任务计划和任务记录都由后端持久化；
2. 面板 Agent 的结构化计划是编排模式和子 Agent 选择的唯一权威来源；
3. 四种模式各有真实 Provider 回归结果；
4. 取消、重试、限流、崩溃恢复和费用上限有自动化测试；
5. 图片和视频任务只有在结果持久保存后才能完整成功；
6. 茶道海报基准任务可以稳定生成、检查并保存到桌面；
7. 普通用户运行正式版不需要手动启动 Docker Desktop；
8. Windows 安装、升级、备份恢复和卸载流程通过干净机器测试；
9. 单元、集成、端到端、安全和无密钥检查全部通过；
10. 代码和上下文已提交并同步到 GitHub。
