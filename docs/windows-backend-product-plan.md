# Honeycomb Windows 后端产品计划

> 决策日期：2026-07-13
> 当前主线：先把 Windows 版后端做成可稳定交付的产品；macOS 研发暂停，保留现有代码，待 Windows 达到发布候选标准后再恢复。

## 产品目标

Honeycomb 的 Windows 版不是一个“能调用模型的演示面板”，而是一套本地多 Agent 工作系统：

1. 用户在项目对话中描述工作；
2. 面板 Agent 判断这是普通交流还是正式任务；
3. 面板 Agent 生成明确的任务名称、编排模式、参与 Agent、验收标准和交付位置；
4. 后端可靠执行，用户能看到任务进度和每个子 Agent 的真实状态；
5. 任务可以取消、重试、恢复，且不会因为重启而丢失或重复花费；
6. 图片、视频、文档等结果必须真正保存并交付，不能只显示“成功”；
7. 正式 Windows 版不应要求普通用户手动操作 Docker Desktop。

## 当前真实链路

```text
对话页
  -> POST /panel/chat（面板 Agent 回复）
  -> 前端用关键词再次判断任务和编排模式
  -> POST /jobs
  -> createJob + startJobWorkflow
  -> DBOS 工作流
  -> createPipelinePlan（后端再次用关键词选择子 Agent）
  -> 四种编排模式
  -> OpenClaw 或 provider-direct
  -> Postgres / 任务文件 / artifact API
  -> 桌面端下载或导出结果
```

这条链路已经能运行，但同一个任务被面板 Agent、前端和 worker 分别判断，容易出现三方结论不一致。任务取消只会先修改数据库状态，正在进行的模型请求不会立刻停止；任务并发没有统一控制；外部媒体下载失败时仍可能把任务标成成功；视频异步任务也还没有完整轮询和取回结果。

## 暂停范围

Windows 发布候选版完成前，以下工作暂停新增功能：

- macOS 环境诊断、bash/zsh 启动脚本、DMG、签名和公证；
- Linux 桌面和服务器发行版；
- iOS、Android 和移动端配对；
- 飞书、微信等新入口扩展；
- Schedule 页面、复杂浏览器自动化和非核心 MCP 扩展；
- 与任务闭环无关的界面装饰性优化。

已经完成的 macOS runner 和 Keychain 代码保留，不回滚，不继续扩展。

## 实施顺序

### 阶段 1：统一“对话 -> 任务”后端契约

目标：面板 Agent 成为唯一的任务规划者，前端只展示和提交，不再自行猜测。

交付内容：

- 在后端持久化项目、对话、消息，以及对话与任务的关联；
- 面板 Agent 返回结构化计划：
  - `intent`：普通回复或任务；
  - `title`：用户能看懂的任务名称；
  - `routingMode`：四种模式之一；
  - `selectedAgents` / `skippedAgents`；
  - `stages`、验收标准、输出类型、交付位置；
  - 模型调用预算和需要补充的问题；
- 后端校验这份计划后原子化创建任务，避免“回复成功但任务没创建”或重复派发；
- 关键词规则只保留为模型不可用时的降级方案，并明确标记为降级；
- 任务名称写入数据库，不再只由界面临时推断。

验收场景：

> “帮我做一个茶道宣传海报，1080×1920，古典华美，无文字，PNG，放到桌面。”

应得到：任务名“茶道宣传海报”；生产 Agent 只选 `image-agent`；`test-agent` 作为质量关卡；跳过 research、writer、video；交付要求明确为桌面 PNG。

### 阶段 2：执行控制与费用保护

目标：任务跑得动，也停得住；失败不会盲目重试或重复扣费。

交付内容：

- 全局、每 Provider、每 Agent 的并发上限和排队状态；
- 取消信号传入正在运行的 HTTP 请求和 OpenClaw 子进程；
- 按错误类型处理重试：
  - API Key、模型名、余额/权限错误不自动重试；
  - 限流、临时网络错误、服务端错误按退避策略重试；
  - 支持 Provider 返回的 `Retry-After`；
- 继续使用幂等记录，补齐“请求已发出但结果未知”的自动修复；
- stalled 任务可从安全检查点恢复，不从头重复执行已成功阶段；
- 在执行前验证所有已选 Agent 的模型、Key、端点类型和账户状态；
- 记录调用次数、Token、估算费用和失败原因。

验收标准：取消后不再产生新的模型调用；认证错误不会连续重试；程序或 worker 重启后不会重复消费已完成的模型调用。

### 阶段 3：统一产物与交付

目标：任务“成功”必须等于用户真的拿到结果。

交付内容：

- 统一图片、视频、文档、外部 URL、Provider 异步任务的产物记录；
- 远程媒体优先保存到 Honeycomb 管理的本地存储，并记录校验值、格式、大小和来源；
- 下载失败进入可重试的交付状态，不能把只有临时 URL 的任务直接标成完整成功；
- 完成视频任务状态轮询、超时、取消和最终文件下载；
- 按用户要求执行 PNG/JPEG 等格式转换；
- 桌面、项目文件夹或自定义位置都通过统一交付任务处理；
- API 提供稳定的预览、打开、另存和重试交付能力。

验收标准：茶道海报任务结束后，桌面存在可打开的 1080×1920 PNG；任务页能预览，并能看到保存位置和交付状态。

### 阶段 4：把四种编排模式做实

目标：四种模式不是四个名称，而是四种可验证的执行行为。

- `supervisor_pipeline`：逐阶段执行，每个生产阶段经过质量检查和有限修正；
- `pipeline`：严格使用上一步产物，最后统一验收；
- `classic_master_slave`：真正并行执行互不依赖的子任务，再由主 Agent 汇总；
- `master_slave_discussion`：保留多方意见和轮次，再由主 Agent 综合结论。

每种模式都要覆盖：动态 Agent 选择、取消、限流、失败恢复、预算、产物、时间线和重启恢复。真实 Provider 测试需要继续获得用户明确授权。

### 阶段 5：Windows 本地运行与安装

目标：开发者可以继续使用 Docker，但普通用户不需要理解或手动操作 Docker Desktop。

交付内容：

- 短期：Honeycomb 启动时先打开界面，明确显示后台状态；未经用户设置，不突然启动 Docker Desktop；
- 正式发行：内置并监管 API、worker 和本地 PostgreSQL 运行环境；
- 保留 Docker Compose 作为开发和诊断模式；
- 提供一键启动、停止、修复、日志包、备份和恢复；
- 安装、升级和卸载不丢失用户项目、对话、配置和任务产物；
- 继续使用 Windows DPAPI 保存 API Key。

验收标准：在一台没有运行 Docker Desktop 的干净 Windows 机器上，安装后能完成首次配置、对话、真实任务、结果交付、退出和再次恢复。

### 阶段 6：发布级收口

目标：形成可重复验证的 Windows 发布候选版。

- 把超大的 `server.ts` 和 `activities.ts` 按已触及的功能边界逐步拆开；
- 建立 API 合约测试、数据库集成测试、四模式回归测试和桌面端到端测试；
- 覆盖断网、限流、Key 失效、磁盘不足、Provider 返回空结果、Docker/进程退出、数据库迁移失败等场景；
- 生成不含密钥的支持日志包；
- 完成数据库和产物备份/恢复；
- Windows 安装包、升级、卸载、签名和干净机器测试通过。

## Windows 发布候选门槛

只有以下条件全部满足，才恢复 macOS 主线：

1. 对话、任务计划和任务记录都由后端持久化；
2. 面板 Agent 的结构化计划是编排模式和子 Agent 选择的唯一权威来源；
3. 四种模式各有真实 Provider 回归结果；
4. 取消、重试、限流、崩溃恢复和费用上限有自动化测试；
5. 图片和视频任务只有在结果持久保存后才能完整成功；
6. 茶道海报基准任务可以稳定生成、检查并保存到桌面；
7. 普通用户运行正式版不需要手动启动 Docker Desktop；
8. Windows 安装、升级、备份恢复和卸载流程通过干净机器测试；
9. 单元、集成、端到端、安全和无密钥检查全部通过；
10. 代码和上下文已提交并同步到 GitHub。

## 下一项开发

确认本计划后，先实施“阶段 1：结构化面板编排契约”。第一小步是把契约类型、校验器和失败降级规则放到后端，并为茶道海报、视频、研究报告和讨论决策四类任务写回归测试。
